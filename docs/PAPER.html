Abstract— Large-language-model (LLM) collaboration tools increasingly host a shared conversational context across multiple human participants. Existing designs concentrate two costs on the service provider: (i) the monetary cost of central LLM inference, including the recurrent cost of context summarization once the dialogue exceeds the model window, and (ii) the security cost of a server-side proxy that relays user-supplied API keys, which introduces a classic server-side request forgery (SSRF) surface. Meanwhile, the rich body of work on recursive and hierarchical context compression implicitly assumes a single user and trusted server infrastructure. We present Aidit, a Reddit-style mobile community in which every post opens a chat-room-like comment thread, and multiple users jointly accumulate a single cumulative AI context with a per-community persona. Aidit's server is deliberately key-blind: it never holds, relays, or logs an LLM key. The browser fetches the Google LLM provider endpoint directly (proxyless BYOK), removing the server-side SSRF surface that proxied BYOK designs incur. When the active context exceeds a 128K-token product-policy threshold, summarization is not performed by the server but is lazily delegated to the next client that triggers an @AI event, which performs recursive summarization with its own key and synchronizes only the resulting text. We do not claim client/edge inference delegation, federated summarization of shared conversations, or BYOK as individually novel—each is documented prior art (closest: US 9,569,428 B2, which already teaches client-side summarization of a multi-user shared meeting with the server as store). Our distinguishing element is the shared-state reconciliation problem this combination creates: a server-side idempotency guard with optimistic concurrency that enforces exactly one summary per active segment across mutually distrusting clients holding different keys and models (winner 201 / loser 409). The architecture drives provider-side LLM inference cost to zero, externalizing each interaction's cost to the triggering client's key quota; total system inference cost is relocated to client key quotas, not eliminated. We describe the system, analyze its security model, and give an analytical cost model. We report results as a proof of concept; quantitative figures are illustrative or expected values unless explicitly derived.
Index Terms— bring-your-own-key (BYOK), large language models, context compression, recursive summarization, server-side request forgery, content security policy, real-time collaboration, server-sent events, multi-tenant systems, cost externalization.

I.  Introduction

Conversational LLM products are migrating from single-user chat toward shared, multi-participant workspaces in which several humans contribute to one accumulating dialogue with an AI agent. This shift exposes three structural problems that the prevailing architectures handle poorly.

Shared multi-user AI context. A single conversation is now a common resource: many users read it, append to it, and trigger AI responses against it. The context is no longer the private state of one client—it must be persisted, fanned out in real time, and bounded by a common token budget. Yet most context-management research models a single client owning a single session.

Cost concentration of central summarization. Once the cumulative dialogue exceeds the model's usable window, the system must compress it. In server-centric designs the provider pays for this summarization inference repeatedly, on top of paying for every reply. As thread count and participation grow, summarization becomes a recurrent, provider-borne tax.

SSRF of proxied BYOK. Bring-your-own-key clients let users supply their own LLM credentials [17]. For request shaping, provider forwarding, or to reconcile browser cross-origin constraints, many open-source BYOK tools route the call through a server-side proxy. When such a proxy accepts a client-supplied destination and issues the outbound request without strict validation, it becomes a server-side request forgery (SSRF) primitive—a tendency that has produced multiple documented critical CVEs in comparable self-hosted chat UIs (e.g., LobeChat CVE-2024-32964; NextChat CVE-2023-49785 and CVE-2026-7177) [7], [8]. SSRF here stems from unvalidated proxying rather than from proxying per se—a hardened allowlisting proxy mitigates it—so a purely client-side design removes this specific server-side surface rather than proving proxying inherently unsafe.

We argue these three problems share one root cause: the assumption that the server should own inference. Aidit inverts that assumption. The server is reduced to text CRUD, a per-thread real-time relay, and the single source of truth for context boundaries. All inference, including summarization, is performed by clients with their own keys, talking directly to the provider. We do not claim the individual ingredients as novel: client/edge LLM inference delegation, federated/distributed summarization of a shared conversation, and BYOK billing are each documented prior art (Sec. II), and US 9,569,428 B2 already teaches client-side summarization of a multi-user shared meeting with the server reduced to a store. No single prior reference, to our knowledge, combines these elements with a server-side coordination contract for reconciling per-user, per-key client summaries of one shared thread. Our contributions are therefore:

  1. A shared-state reconciliation contract for distributed summarization. Our central element: a per-post idempotency guard with optimistic concurrency (winner 201 / loser 409) that enforces exactly-one-summary-per-active-segment semantics when mutually distrusting clients—holding different keys and possibly different models—each independently compress the same shared thread. We distinguish this from US 9,569,428 B2, which offloads summarization to clients but does not address cross-client summary reconciliation under per-user keys.
  2. A key-blind, proxyless multiplayer BYOK integration. The browser fetches the provider endpoint directly; the server never holds or relays a key, removing the server-side SSRF surface that proxied BYOK clients incur (Sec. V), applied to a multi-user collaborative space rather than a single-user chat.
  3. Client-driven lazy summarization. Because a key-blind server cannot summarize on its own, the 128K-token threshold is enforced lazily: the next client to trigger an @AI event performs recursive summarization with its own key, and synchronizes only the summary text.
  4. Provider-side cost externalization of a shared context. The compute and transport cost of maintaining a shared (commons) context is externalized to the triggering client's key quota, driving provider-side LLM inference cost to zero; total system cost is relocated to client key quotas, not eliminated.

II.  Background and Related Work

A. Context-Length Limits and Compression

LLMs operate within a bounded context window, and effective use degrades well before the nominal limit. A large literature addresses this with summarization-based compression: recursive summarization repeatedly condenses earlier dialogue into a running summary, rooted in Wu et al. [1] and adapted to zero-shot hierarchical merging in later work [2], and the Hierarchical Aggregate Tree (HAT) [3] builds a depth-controlled tree over dialogue history (a single 2024 preprint, not an established standard); map-reduce and refine chains [4] are the corresponding engineering patterns. Retrieval-augmented and memory-augmented schemes externalize history into a store and re-inject the relevant slice [5], [6]. These methods are effective, but they are formulated for a single agent operating over trusted server infrastructure: the summarizer is the server, the cost is the server's, and there is no notion of multiple mutually untrusting key-holders sharing one context.

B. BYOK Clients and the Server-Proxy SSRF Surface

Open-source BYOK chat clients such as NextChat and LobeChat let users supply their own provider keys [7], [8]. For provider forwarding, request shaping, or chat-data sync, such deployments frequently introduce a server-side proxy that forwards a request to a client-influenced destination. When that destination is accepted without strict validation, the proxy becomes a server-side request forgery (SSRF) primitive [9], [10]; this is an empirically strong tendency rather than a logical necessity, as a hardened proxy with allowlisting and DNS-rebinding defenses mitigates it. The pattern has nonetheless produced multiple documented critical CVEs in this software class—LobeChat CVE-2024-32964 (CVSS ~9.0, an unauthenticated proxy passing raw input to fetch()) and NextChat CVE-2023-49785 and CVE-2026-7177 (the latter an unvalidated x-base-url provider proxy)—and combined with key handling the proxy becomes both an SSRF vector and a credential chokepoint [7], [8]. Aidit takes the opposite route: no proxy exists, so this server-side SSRF surface does not exist; the design relocates rather than removes risk (Sec. V, Sec. VII).

B′. Client-Side and Federated Inference (Closest Prior Art)

Offloading LLM inference to the client or edge is well established: in-browser LLM execution [19], split/private inference [20], and federated/collaborative inference over edge networks [21] all move heavy inference off the central server for cost or privacy. Most relevant, US 9,569,428 B2 [22] teaches performing summarization on client devices for a multi-user shared online meeting, with the server reduced to storing the resulting summaries—anticipating client-side summarization, multi-user shared context, and server-as-store as a combination. Its summarizer is heuristic/metadata-based rather than an LLM, and it does not address reconciling multiple clients' independent summaries of one thread under per-user keys. We cite it as the closest prior art and distinguish Aidit by the cross-client reconciliation contract of Sec. IV/D.

C. Central NLP Summarization Patterns (Contrast)

Commercial transcription and meeting-intelligence systems collect the conversation into a cloud service that performs the NLP summarization server-side. Concrete prior art includes Otter.ai's live-summarization patent [11], whose "live summary processing unit" returns server-generated summaries to client devices, and IBM's meeting-digest patent [12], which performs NLP analysis on a "meeting digest server device." Deployed systems follow the same cloud-by-default pattern: Samsung's Galaxy AI Transcript Assist [13] transcribes on-device but, by default, summarizes in the cloud (with an optional on-device processing toggle), so it is a hybrid, cloud-by-default system rather than a centralized-summarization patent holder. This cloud-by-default actor pattern is the precise inverse of Aidit's design, which moves the inference actor to the client; we use these systems as a point of contrast rather than as components.

D. Shared Live Sessions and Auto-Compaction

Aidit's collaboration model was inspired by the open-source agent-cli project [14] (MIT), which demonstrates (i) multiple viewers sharing one live AI session with concurrent intervention via fan-out, and (ii) automatic summarization once the context fills toward a high-water mark. However, agent-cli assumes a single session in a single process, stores the key on the server, supports nicknames only, and persists to JSONL—none of which fits a multi-tenant community. We port the summarization pattern to client-side TypeScript and build a new multi-tenant, key-blind backend around it.

III.  System Architecture

A. Design Principle: A Key-Blind Server

Aidit is a Reddit-style mobile-first community. Each post opens a chat-room-like comment thread; within it, multiple users co-accumulate a single AI context and collaborate with a per-community persona AI. The server intentionally does only three things: (a) text CRUD, (b) per-thread real-time relay (SSE fan-out), and (c) serving as the single source of truth (SoT) for context boundaries (segments). It never holds, fronts, or transits an LLM key. Everything the server receives is already-generated text: a human comment, an AI reply, or a summary.

B. Proxyless Browser→LLM Direct Fetch

All inference is a direct browser fetch to the provider:

https://generativelanguage.googleapis.com/
v1beta/models/{MODEL}:generateContent?key={USER_KEY}

Google documents the ?key= query-parameter form (and an x-goog-api-key header alternative) for the v1beta generateContent/countTokens endpoints [16]. Direct browser-side calling with an embedded key is a deliberate BYOK deployment choice that diverges from Google's own guidance, which recommends a backend proxy and warns against client-side key exposure; the CSP and localStorage mitigations of Sec. V exist precisely to address the resulting client-side key-exposure risk. The PoC pins LLM_MODEL = gemini-3.1-flash-lite (Google Gemini Flash Lite, GA 2026, ~1,048,576-token input window) [16]. Because there is no server proxy, the server-side SSRF surface that proxied BYOK clients incur does not exist (Sec. V).

C. ContextSegment as the Single Source of Truth

The unit of context boundary is the ContextSegment. A post creates segment #0 automatically. Exactly one segment is active (isActive=true). Each segment carries a tokenSum, and tokenSum is the single source of truth for the 128K threshold decision. The active context is defined as:

  • Segment 0: the post body plus every bubble in segment 0.
  • Segment N (N≥1): the AI_SUMMARY bubble that opens segment N, plus the bubbles of segment N—the pre-summary history is excluded (recursive compression).

Thus summaryNeeded = (activeSegment.tokenSum > 128000). Fig. 3 shows the segment state transition.

D. SSE Fan-Out and Data Model

Writes go over REST; the server fans out every state change to all thread viewers over server-sent events (one-directional server→client) [18]. The client opens the stream with an outbound HTTP GET (and may resend Last-Event-ID, here the seq replay key, on reconnect) but cannot push data over the event stream itself. The data model (Prisma) is: User (no key stored; guest passwordHash=null); Community (with personaPrompt as the persona basis for the system instruction); Post; Comment (the bubble: type∈{HUMAN, AI_REPLY, AI_SUMMARY}, status∈{PENDING, COMPLETE, FAILED}, with tokenCount, segmentId, and a monotonically increasing seq used as the SSE replay/idempotency key); ContextSegment (index, summaryCommentId?, tokenSum, isActive); plus Bookmark and Vote.

IV.  Client-Driven Lazy Summarization

A. The @AI Sequence

The client orchestrates the entire interaction (TRD §6.2); Fig. 2 is the flowchart. (1) A user sends an "@AI ..." comment; REST registers the human comment first as type=HUMAN, status=COMPLETE so it appears immediately. (2) The client GETs /posts/:id/context, receiving {segmentIndex, contents[], tokenSum, summaryNeeded} assembled by the server from the active segment only (the server has no key). (3) If summaryNeeded, the lazy summarization branch runs (below). (4) The client POSTs an AI_REPLY bubble as PENDING (with replyToId set to the human comment), surfacing a loading indicator to all viewers over SSE. (5) The caller calls the LLM provider's generateContent with its own key (systemInstruction = persona, contents = the assembled context). (6) The client PATCHes the AI bubble with the reply and status=COMPLETE (or FAILED on error); the human comment is never lost (NFR-5). (7) The server fans out at every step.

B. Why Lazy, and the 128K Policy Threshold

The 128K threshold is a product-policy threshold for the active segment—distinct from any particular model's context window—chosen to bound the assembled context that a triggering client must pay to process. The pinned model's documented input window is ~1,048,576 tokens [16], so 128K (131,072) sits ~8× below it, confirming the threshold is a cost/policy ceiling and not a technical one. Because the server is key-blind, it cannot summarize the moment a bubble pushes the segment past 128K. Even a burst of ordinary human comments can cross the threshold without any AI call. Summarization is therefore deferred (lazy) to just before the next @AI call, when a key-holding client is, by definition, present and about to perform inference anyway.

C. Recursive Context Reassembly

In the lazy branch (Fig. 2, step 3): (a) the caller calls the LLM provider with systemInstruction = persona + summarization-directive and contents = the current active context, producing a summary; (b) the client POSTs an AI_SUMMARY bubble with segmentExpected = current active index, and the server opens and activates a new segment N+1; (c) the client re-GETs /context, now reassembled as summary turn + subsequent bubbles only. The pre-summary history is dropped from the active context, realizing recursive compression (Fig. 3). Both the AI reply and the summary are produced in the active UI locale, enforced by a language directive appended to the system instruction (i18n: ko/en).

D. Concurrency Idempotency Guard

Two clients may trigger summarization concurrently (BE-7). The server enforces a per-post idempotency guard: at most one AI_SUMMARY per active segment. The first summary POST (the winner) opens the new segment and receives 201; the second (the loser) receives 409 together with the latest segment, and proceeds against the new segment. On any segmentExpected mismatch the server corrects the client (optimistic concurrency). Fig. 4 is the sequence diagram. The human comment is never lost regardless of branch outcome.

V.  Security Analysis

A. Threat Model and CSP as a Scripted-Connection Control

Attacker model. We assume an XSS-capable in-page script (able to read localStorage and issue requests in the page's origin) and an honest-but-curious server (it stores and relays text faithfully but should never learn a key or model output it did not store). The API key lives only in the browser's localStorage and, transiently, in memory immediately before a call. It never appears in any server request body, header, or log. The primary mitigation against key exfiltration under XSS is a strict Content Security Policy [15] that sets default-src 'none' and an explicit connect-src allowlist:

default-src 'none'; connect-src 'self' https://generativelanguage.googleapis.com;

A connect-src allowlist of 'self' plus the provider host prevents an injected script from exfiltrating the key via the four scripted-connection channels connect-src governs—fetch/XHR, WebSocket, and EventSource (and sendBeacon/anchor ping)—because the browser refuses such requests to non-allowlisted hosts before they leave. This is not a complete anti-exfiltration boundary: connect-src does not cover image/resource loads (e.g., new Image().src), top-level navigation, window.open, or form submission, DNS-prefetch/preconnect/prerender, or WebRTC. Closing those residual channels requires separate directives, which is why the policy also sets default-src 'none' (which, as the fallback for the absent img-src, blocks image-based GET exfiltration), script-src 'self', object-src 'none', base-uri 'self', form-action 'self', and frame-ancestors 'none'. Even so, CSP is a mitigation, not a guarantee; the residual channels (notably DNS-prefetch and WebRTC, which CSP does not constrain) are enumerated in Sec. VII.

B. Elimination of the Server-Side SSRF Surface

Proxied BYOK designs expose SSRF when a server endpoint forwards requests to an unvalidated destination on the client's behalf. Aidit has no such proxy: the browser calls the provider directly, so there is no server-mediated outbound-request primitive to abuse. This eliminates the server-side SSRF surface by construction rather than by filtering. It does not make the system risk-free: it relocates exposure to the browser-resident key (subject to XSS theft, Sec. V/A) and to client-side CORS constraints, rather than removing all risk.

C. Prompt-Injection Isolation

Only community.personaPrompt is mapped to the systemInstruction (XC-4). All user and comment content is always mapped as role:'user' data turns and can never be promoted to the system role. buildLlmRequest is the single point where this mapping occurs, and every appended turn is forced to role:'user'. Fig. 5 depicts both the CSP egress control and the proxyless (no-SSRF) topology.

VI.  Cost Model and Evaluation

A. Analytical Cost Model

Let a thread accumulate R AI replies and require S summarization passes over its lifetime, and let cr and cs denote the token cost of a reply and a summary. In a central-summarization design the provider pays Ccentral = R·cr + S·cs. In Aidit every reply and every summary is executed by the triggering client against its own key, so the provider's LLM inference cost is

Cserver, LLM = 0,

and the per-interaction cost cr (and the amortized cs when that client happens to cross 128K) is charged to that client's key quota. The provider operates only CRUD + SSE-relay infrastructure. This is an analytical, structural result, not a measured speedup: it follows directly from the key-blind, direct-fetch design.

The result is conditional. Cserver, LLM = 0 holds only while the server issues zero generateContent and zero key-bearing countTokens calls. The key-free Math.ceil(chars/4) token fallback (Sec. VI/B) is the assumption that preserves this: it keeps tokenSum server-computable without a key, so the server never needs to call countTokens itself. The claim would be falsified if the server ever held a fallback key, proxied countTokens, or added a server-side moderation/inference pass—any of which reintroduces provider-side cost.

B. Token-Counting Method

On bubble post, tokenCount is computed by the LLM provider's countTokens as the primary, accurate method (requires a key), with a key-free fallback of Math.ceil(chars/4). The server accumulates segment.tokenSum += tokenCount; GET /context returns this tokenSum, which is used verbatim for the 128K threshold decision.

D. Threats to Validity and Reproducibility

The cost result is analytical, not measured (Sec. VI/A), and its falsification conditions are stated there; we have not characterized the constant factors of the CRUD/SSE-relay infrastructure under load. The security claims are scoped to the stated attacker model (Sec. V/A): connect-src blocks only the scripted-connection channels, and residual channels remain (Sec. VII). The novelty claim is exposed to prior art—the individual ingredients are known (Sec. II)—so the contribution rests on the cross-client reconciliation contract rather than on the architecture per se. Reproducibility. The PoC stack is React 18 / Vite / Zustand / Tailwind on the client and Node 20 / Fastify / Prisma with SQLite→PostgreSQL on the server; no measurement artifacts are reported, and any quantitative figures are illustrative or expected unless explicitly derived.

VII.  Limitations and Future Work

  • Cost-transfer fairness (UX). Externalizing shared-context cost to whichever client happens to trigger an @AI event—especially the unlucky client that crosses 128K and pays for summarization—raises fairness questions that need UX and possibly accounting mechanisms.
  • Summarization-quality evaluation. Recursive compression can lose information; a quality evaluation loop (faithfulness, recoverability) is future work.
  • Concurrency non-determinism. The winner/loser race resolves correctness but the content of the winning summary is non-deterministic in the PoC.
  • Guest→member promotion. Guests (nickname#hex4, passwordHash=null) currently cannot carry state into a registered account.
  • Multi-provider. The PoC pins Google Gemini; generalizing the direct-fetch and token-counting layers to other providers remains open.
  • Residual exfiltration channels. CSP connect-src governs only fetch/XHR, WebSocket, and EventSource. Image/resource loads, navigation / window.open / form submission, DNS-prefetch/preconnect/prerender, and WebRTC are not covered by connect-src and must be closed by separate directives (default-src 'none', restricted img-src, form-action); DNS-prefetch and WebRTC in particular are documented CSP gaps, so the key-exfiltration mitigation is strong but not complete, and the client-resident key remains subject to XSS theft.
  • Prior-art exposure. Client/edge inference, federated summarization of shared conversations, and BYOK are individually known (Sec. II), and US 9,569,428 B2 is close prior art; the defensible contribution is the cross-client summary-reconciliation contract, and a formal novelty/non-obviousness assessment against the broader patent landscape is future work.

VIII.  Conclusion

Aidit demonstrates that a multiplayer AI workspace can run with zero provider-side LLM inference cost and no server-side SSRF surface by making the server key-blind and delegating all inference—including summarization—to clients via direct provider fetch; total system cost is relocated to client key quotas rather than eliminated. The component techniques— client/edge inference, BYOK, and federated summarization of shared conversations—are each known prior art (closest: US 9,569,428 B2); our distinguishing element is the server-side contract that reconciles per-user, per-key client summaries of one shared thread. A 128K product-policy threshold over a single-source-of-truth context segment, enforced lazily at the next @AI trigger, realizes recursive compression of a shared context, while a winner/loser idempotency guard keeps concurrent summarization safe. We present this as a proof of concept and invite evaluation of summarization quality and cost-fairness in deployment.
